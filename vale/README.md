# STE — a Vale style distilled from ASD-STE100

Rules distilled from the Boeing/ASD **Simplified Technical English** standard
(ASD-STE100, Issue 9), scoped to one goal: make AI-agent-written markdown
(specs, plans, docs) read cleanly for a non-native English speaker working
with LLMs. This is a baseline for a future Claude Code hook — not a full port
of the standard, which targets aircraft maintenance manuals and includes
rules (safety instructions, part-naming categories, procedural work-step
grammar) that don't transfer to spec-writing.

## Run it

```bash
mise use vale   # once, if not already installed
vale --config vale/.vale.ini vale/fixtures/bad.md   # should report violations
vale --config vale/.vale.ini vale/fixtures/good.md  # should be clean
```

## Layout

```
vale/
  .vale.ini            StylesPath + MinAlertLevel=suggestion, applies to *.md
  styles/STE/*.yml      one rule file per concern, `extends:` a Vale check type
  fixtures/{good,bad}.md  hand-written regression fixtures
```

## Deliberately left out

Triaged out because they either don't transfer from aircraft manuals to specs,
or are too subjective/false-positive-prone to enforce mechanically without
training everyone to ignore the linter:

- **Section 5** (procedural writing: imperative-only, one instruction per
  sentence) and **Section 7** (safety instructions) — genre-specific to
  maintenance procedures, not prose docs.
- **Rules 1.5–1.12** (technical-noun/verb categories) and **2.1–2.2**
  (3-word multi-word-noun cap) — aircraft-parts vocabulary work, not
  applicable to software specs.
- Present-perfect / progressive-tense bans (3.2/3.4), phrasal-verb ban (9.3),
  pronoun-ambiguity (GR-3/GR-4), "with"-ambiguity (GR-2), inclusive-language
  (GR-7) — real STE rules, but regex-checkable versions produce too many
  false positives on legitimate spec prose ("we have decided", "the daemon is
  processing"). Revisit if `sequence` (POS-tagged) checks turn out reliable
  enough.

## Composability

`Vocab.yml` and `AmericanSpelling.yml` are the two files meant to grow or get
regenerated by a future "build a dictionary from this machine's context"
skill — the swap map only lists synonyms, so a new file can add entries
without touching the structural rules (sentence/paragraph length,
contractions, semicolons). Keep new dictionary work in files that only
`extends: substitution`, not mixed into the structural rule files.

## Dogfood results

Ran against real, unmodified prose this style wasn't tuned against
(`CLAUDE.md`, this README) to check noise rather than just confirm the rules
fire:

- List items are scoped individually by Vale's markdown parser, not lumped
  into one `paragraph` scope — a 7-item list where every bullet ends in a
  period does **not** trip `ParagraphLength`. Verified with a throwaway
  fixture; no false positive.
- `ParagraphLength` did catch one real dense paragraph in `CLAUDE.md`
  (the session-navigation paragraph) — a true positive, not a list artifact.
- `PassiveVoice`'s `\w+ed` originally matched short adjectives like "red" as
  if they were past participles (`should be red` → false "passive" flag).
  Fixed by requiring 3+ letters before "ed". It still can't distinguish a
  genuine passive ("must be fixed by the operator") from a past-participle
  used as an adjective ("must be fixed-width", permitted under STE 3.3) —
  that needs real parsing, not regex. Left as suggestion-level for that
  reason; don't promote it without a smarter check.
- No level in this style set is currently `error` — nothing here blocks
  Vale's own exit code by default. `Contractions.yml` was deliberately
  brought down from `error` to `warning`: blocking an agent's whole turn
  over "don't" vs. "do not" is disproportionate for a style rule, and the
  future hook's blocking semantics aren't decided yet. Revisit deliberately
  when that hook exists, not by leaving a level unexamined.
- `Consistency.yml`'s first draft included `repo: repository` and fired
  **8 times** on `CLAUDE.md` alone — pure register variation, not genuine
  reader confusion. Dropped that pair; the other seven (frontend/front end,
  backend/back end, etc.) fired zero times on the same file. The lesson:
  a consistency pair only earns a place here if switching between the two
  forms would actually confuse a reader, not just read informally.

## Notes on the Vale mechanics

- `occurrence` + `scope: sentence`/`paragraph` + `token: '\S+'` counts raw
  word-ish tokens per scope — this is what implements the word/sentence caps,
  not the `metric`/readability-formula check (that runs at document scope).
- `substitution`'s `message` format args are `(replacement, match)`, in that
  order — easy to get backwards.
- Patterns that start or end on a non-word character (`;`, `e.g.`) need
  `nonword: true`, or Vale's automatic `\b` wrapping silently kills the match.
- Go's `regexp` (RE2) has no lookahead/lookbehind — heuristics like
  `MissingThat.yml` use a positive list of risky follow-up words instead of
  a negative lookahead for `that`.
- `consistency`'s `message` takes exactly one `%s` (the term that broke
  consistency) — unlike `substitution`'s two. It flags whichever spelling in
  an `either:` pair shows up *after* the other has already been established
  as accepted; when both spellings land in the same paragraph it flags both
  occurrences rather than just the second — cosmetic, not a bug.
